## 1. Что просит Дима (дословно, две задачи)

**Задача 2 — Маршрутизация.** Ежедневно **до 9:00** на основе всех листов базы бот
составляет рабочий маршрут каждого менеджера и шлёт Диме в Telegram —
**одно сообщение = маршрут одного менеджера**. Формат:

```
<дата> — <Имя Фамилия менеджера>
1. <Название объекта, если есть> — <адрес> — <лист базы> — <станции метро>
2. ...
```

Дима реагирует: **«ок»** (одобрено) либо **голосовым** с правками. Бот
транскрибирует голос и правит маршрут. Пока маршрут не одобрен — **напоминает**.
Когда все маршруты дня одобрены — работа на дату закрыта.

**Задача 3 — Мониторинг Avito/Cian.** Дима отдаёт несколько сохранённых
поисков (ссылки-фильтры) как ТЗ. Ежедневно **в 9:30** бот шлёт сообщение с
шапкой «Avito, Cian <дата> обновление» и **пронумерованными ссылками на новые**
объявления по каждому запросу (с указанием, какая ссылка по какому запросу).
Дима отвечает номерами интересных. Ближайшие адреса одобренных объявлений бот
**добавляет в маршрут** менеджеров (стык с задачей 2).

## 2. Решения, уже принятые (ответы Эдуарда 2026-07-28)

1. **Источник «БАЗЫ» — NocoDB поверх нашего Postgres**, не Google Sheets. Маршруты
   строим из `kosmos.objects` / витрины, не из внешнего Google-документа.
2. **Модель менеджеров — позже.** Кто менеджеры, сколько объектов в день, есть ли
   территории — решит Дима. До ответа маршрутизацию не финализируем (см. вопросы).
3. **Транскрипция — OpenAI Whisper API.** Новая внешняя зависимость: ключ OpenAI + $.
4. **Адаптеры** — модуль-переходник под один сайт (как `src/sources/competitors/*`).
   Для Avito и Cian — по адаптеру на площадку.
5. **Движок одобрений** — общий для обеих задач компонент (раздел 5).

## 4. Чего нет и надо построить

- **Станции метро у адреса.** В коде метро нет. Тянуть станции из OSM (`overpass.js`
  уже есть) один раз в справочник → `nearest` по координате объекта.
- **Модель менеджеров** — таблица `managers` (имя, дневная норма, домашняя точка/
  территория). Заполняется, когда Дима ответит.
- **Движок одобрений** (раздел 5) — самый крупный кусок, общий на две задачи.
- **STT-обёртка** над Whisper — скачать `voice.ogg` из Telegram → Whisper → текст.
- **Адаптеры Avito и Cian** — новые объявления по сохранённому поиску + дедуп.
- **Планировщик** — «до 9:00» и «в 9:30» (n8n или node-cron; **не трогать чужие n8n-воркфлоу**).

## 5. Общий движок одобрений (ядро обеих задач)

Обе задачи — один паттерн: *бот отправил → ждёт вердикт → нет вердикта → напоминает*.
Выносим в один компонент, чтобы не писать дважды.

**Таблица состояния (Postgres):**

```
approvals(
  id, kind ('route' | 'monitoring'),
  target_date DATE,
  subject TEXT,             -- имя менеджера / 'avito-cian'
  payload JSONB,            -- сам маршрут / список ссылок
  message_id BIGINT,        -- id отправленного telegram-сообщения
  status TEXT,              -- 'sent' | 'approved' | 'edited'
  reminders_sent INT,
  created_at, updated_at
)
```

**Жизненный цикл:**
1. Утренний прогон формирует payload, шлёт сообщение, пишет `status='sent'`.
2. Ответ Димы соотносится с записью: reply-to или последнее `sent` того же вида.
   - «ок» → `approved`.
   - голос → Whisper → tool-loop правит payload → перешлём новый → снова `sent`.
   - номера (для мониторинга) → отмечаем выбранные → адреса уходят в маршрут.
3. Крон-напоминалка: `sent` дольше N часов → повторное сообщение, `reminders_sent++`.
4. Все записи даты `approved` → день закрыт.

**Почему отдельно:** текущий бот — stateless Q&A, ничего не «ждёт». Здесь нужна
память ожидания и соотнесение ответа с отправленным. Это ядро; маршрутизация и
мониторинг — тонкие модули поверх него.

## 6. Архитектура (снизу вверх)

```
approval-engine (state + reminders)        ← общий
  ├── routing        managers + metro + nearest + сборка маршрута
  └── monitoring     adapters(avito, cian) + dedup + сборка списка
telegram-io (расширенный run_bot: voice, reply, исходящие)
scheduler (n8n/cron: 09:00 маршруты, 09:30 мониторинг)
whisper-stt (voice.ogg → текст)
```

Инварианты КОСМОСа не нарушаем (HANDOFF §8): машина не удаляет; частичный сбой
источника не молчит; провенанс у каждого значения; ЭЦП Росреестра никуда не шлём.

## 7. Порядок работ (предложение)

1. **Справочник метро** из OSM + `nearest` — маленько, ни от кого не зависит.
2. **Движок одобрений** (таблица + жизненный цикл + напоминалка) — ядро.
3. **Расширить telegram-io**: исходящие, reply-соотнесение, скачивание voice.
4. **Whisper-STT** обёртка.
5. **Маршрутизация** — как только Дима ответит про менеджеров (раздел 8).
6. **Адаптеры Avito/Cian** + дедуп + формат списка.
7. **Планировщик** 09:00 / 09:30.
8. **Стык**: одобренное объявление → ближайший объект → строка маршрута.

Плюс отдельно — **досбор Арендатора** (сейчас 2 из ~9 страниц): адаптер по
чистому JSON-LD arendator.ru для полной сверки БЦ ≥10к.

## 8. Вопросы Диме (без ответов дальше не финализируем)

**Маршрутизация**
1. **Кто менеджеры** — список имён/фамилий? Сколько их сейчас?
2. **Сколько объектов в маршруте** одного менеджера на день?
3. **Как делить объекты** между менеджерами — по районам/территориям, по листам
   базы, по близости к его «домашней» точке, или ты назначаешь вручную?
4. **Из каких листов** брать объекты в маршрут — все 7 или приоритет (сначала БЦ)?
5. **Уже посещённые/отработанные** объекты исключать из будущих маршрутов? Как
   помечаем «был, результат такой-то» — это вердикт в базе?
6. **Время «до 9:00»** — по каким дням? Каждый день, только будни?

**Мониторинг Avito/Cian**
7. Пришли **сами ссылки сохранённых поисков** (по одной на запрос) — это и есть ТЗ.
8. «Новые» — с момента **прошлого прогона** (сутки) или за какой период?
9. Что считать «объектом» на площадке — только **аренда офисов/помещений**, или
   и продажа? Есть ли ограничение по площади/цене (обычно оно уже в фильтре)?

**Охват базы (по итогу сверки Арендатора)**
10. Нужны ли в базе **БЦ Подмосковья** (Химки, Красногорск, Мытищи…)? Сейчас база —
    строго Москва. Если да — это расширение источников, отдельный объём.

**Голос и напоминания**
